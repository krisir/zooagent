# ADR-0014 应用页面只管数据：删除、固定、升级都不在页面上

- 状态：确定（取代 ADR-0010「删除助手从首页卡片移到应用页头」一节；补充 ADR-0013 的页头内容）
- 日期：2026-10-20

## 背景

ADR-0010 把删除助手从首页卡片挪到了应用页头，和「固定」「让主助手升级」并排。ADR-0013 又把页头压到只剩应用标题、这几个按钮和刷新。

实际用下来，页头变成了一个「什么都有点」的操作栏，而且方向是错的：

- **删除**是结构级、不可恢复的操作，放在数据页页头意味着它可以被误点到，也意味着"每个助手页面都得自己实现一遍删除流程"。
- **固定**在应用页头上没有意义：真正需要排序的是左栏列表，而左栏没有星标入口；结果这个偏好只能从应用页里设置，还经常被忘记。
- **让主助手升级**把一句话的诉求包装成一个按钮，但它本质上就是"切到主助手说一句话"，不如直接在主助手对话里说，还能带上上下文。

主助手才是应用的创建者和管理者（ADR-0002 / ADR-0010）。结构操作本来就该回到它那里。

## 决策

### 1. 应用页面不再提供删除

- 删除 `Popconfirm` 删除按钮与 `ApplicationView.onDelete`、`App.deleteApplication`。
- 用户在主助手里说「删掉客户管理」→ 主助手复述 → 用户确认 → 调用新的主助手工具 `delete_application`。
- 工具签名 `delete_application(application_id, confirm_name)`：`confirm_name` 必须与应用名完全一致，否则报 `validation_error` 并且不删除任何东西。这挡住了模型拿错 id 或猜错名字的情况。
- 应用助手（`build_application_tools`）**没有**删除工具，权限边界仍然是：业务数据归应用助手，结构归主助手（有测试固定这一点）。
- 删除后前端刷新列表；如果当前打开的正是被删的助手，`App` 会把 `currentAppId` 收回主助手首页。

### 2. 页头不再有固定与升级

- 移除「☆ 固定 / ★ 已固定」与「让主助手升级」两个按钮。
- 随之移除 `lib/prefs.ts`（星标偏好）与左栏的 `★` 标记：没有入口的偏好只会变成死代码。左栏列表按 `updated_at` 倒序（`Rail` 只剩这一个排序键）。
- 应用页头只剩：标题 / 元信息 + 刷新按钮。数据页收起时连它一起收起（ADR-0013）。

### 3. 主助手的提示词要写清删除流程

`PRIMARY_PROMPT` 增加一条硬性规则：删除助手只能用 `delete_application`，必须先复述名称并得到明确确认；应用页面上没有删除按钮，主助手对话是唯一入口。工具描述里同样写明不可恢复与 `confirm_name` 要求。

## 代价与边界

- **删除路径变长**：一次对话（复述 + 确认）换来不可逆操作的安全性。可以接受——删除助手本来就很少发生。
- **删除了星标能力**：列表回到单一的 `updated_at` 排序。如果之后确实需要置顶，应该在左栏列表项上提供星标入口，而不是回到应用页头（ADR-0010 也提过：不要再在 localStorage 里堆影子数据）。
- **升级入口变远**：想改结构必须先点左栏的主助手。好处是请求能带上真实上下文（"把刚才那个字段改成必填"），坏处是少了一次跳转。
- **软删除**：`delete_application` 仍是标记 `status='deleted'`，应用数据目录还在磁盘上。真正的物理清理属于备份/回收站话题，不在本 ADR 范围。

## 验证

- `apps/desktop`：`pnpm exec tsc --noEmit`、`pnpm build` 通过；应用页头只剩一个刷新按钮。
- 后端：`pytest` 全绿。新增用例覆盖：
  - `delete_application` 在 `confirm_name` 不匹配时报错且不删除；匹配时应用从列表消失；
  - 应用助手的工具集里没有 `delete_application`；
  - 主助手提示词包含删除走对话的规则。
- `capture_ui.py` 仍无 JS 异常与控制台错误。
