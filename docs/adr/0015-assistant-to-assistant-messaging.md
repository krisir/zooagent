# ADR-0015 助手之间可以互相发消息：主助手做枢纽，被联系时只读

- 状态：确定
- 日期：2026-11-02

## 背景

用户在一个应用的对话里提的诉求，未必是这个应用能做的：

> 「把经期助手改温柔一点，别每次都甩一堆数字。」

这句话本质是**结构变更**（改助手指令 / 加字段 / 重做页面），属于主助手的权限。
在此之前应用助手只有两条路：含混地拒绝（"我只能查这个应用的数据"），或者越界假装能改。
用户得自己意识到"要去主助手那边再说一遍"，并且要重新描述一遍上下文。

另一种方向同样缺失：主助手升级完一个应用后，没有任何办法让那个应用的助手去核对现状
（"你那边现在有几个字段？"），只能等用户回去问。

## 决策

### 1. 通信拓扑：应用助手 ↔ 主助手，不开放应用之间

- 应用助手可以用 `send_message_to_primary` 找主助手；
- 主助手可以用 `send_message_to_application` 找某个应用助手（先 `list_applications` 拿 id）；
- **禁止应用 ↔ 应用**：一个应用的数据不能因为"另一个助手问了一句"而流出这个应用
  （ADR-0002 的隔离不变量）。

### 2. 被联系的主助手只读

`AgentFactory.for_messaging(sender)` 只挂 `list_applications` / `get_application_overview`，
system prompt 明确：给方案，不执行。原因有两条：

- 应用助手的上下文里可能混入业务数据，甚至混入被污染的文本；一条转达的消息不该能直接
  触发结构写入；
- 「改动要用户确认」这条规则需要有唯一可信的确认来源。主助手对话里用户亲手打的"确认"，
  才是那个来源（与 ADR-0011 的 Action 修复、ADR-0014 的删除应用同一个思路）。

所以流程是：应用助手转达 → 主助手出方案（结尾提示"在主助手对话里回一句确认"）→
应用助手把方案转述给用户 → 用户切到主助手对话确认 → 主助手用正常写工具执行。

### 3. 投递是异步的：先回答，答复稍后到达

工具调用不阻塞对方的回合，只把消息排进本轮的 outbox（`ToolRegistry.outbox`）。
本轮回答写完之后，`chat.py` 才逐条投递：

1. 为对方跑一次有界的回合（`MESSAGE_TIMEOUT_SECONDS = 90`）；
2. 把「收到了谁的消息」记进对方对话（role=user，metadata.kind=agent_message，direction=in），
   再把对方的回答记成这条会话里的普通 assistant 消息 —— 这就是"助手在自己的对话框里
   给用户发消息"；
3. 把「回复了谁」记进发起方对话（role=assistant，metadata.kind=agent_message，direction=out），
   同时以 `agent_message` 事件推给前端。

投递用一个 `asyncio.shield` 的任务：用户点「停止」只停止流，不会把已经说出口的"已转达"变成空话。

### 4. 呈现：一行折叠卡片

两边的对话都留一张卡片：

- 接收方：「收到了「个人记账」的消息」
- 发送方：「回复了「主助手」」

卡片本身是一个入口：点一下直接跳到对方的对话，那里有完整的原文（对方的自述、
方案、上下文）。理由：助手之间的往来是**过程**，不是对话本身；用户要的是"这件事
有人接住了"，而"读全文"最好的地方是对方自己的对话框，不是把长文塞进当前这层气泡。

没有跳转能力的地方（例如页面里内嵌的 ChatPanel）退回成就地展开，卡片内容仍然可读。

### 5. 不回声，不成环

接收方跑的那次回合**不注册**发消息工具（`application(..., with_messaging=False)`），
主助手的 relay 注册表也只有读工具。两个助手不可能互相踢皮球。

## 影响

- 应用助手的 prompt 增加了"什么时候找主助手"；主助手的 prompt 增加了"收到了别人转来的请求"。
- 新增 `agents/messaging.py`（outbox、`AgentMessenger.deliver`、两个注册函数）。
- 新增流事件 `agent_message`；消息 metadata 增加 `kind/direction/peer/request/reply`。
- 新增两张卡片样式 `.agent-msg`，与会话中的普通气泡区分。
- 新增集成测试 `tests/integration/test_assistant_messaging.py`（双向各一条）。

## 未做

- 应用 ↔ 应用的消息（会打破数据隔离，除非先设计跨应用授权）。
- 主助手被联系时的"待确认提案"持久化：目前确认靠主助手对话里的自然语言，
  提案本身留在会话历史里。
- 多轮协商（助手之间连续多次往返）：每次转达都是独立的一轮，够用且可解释。
